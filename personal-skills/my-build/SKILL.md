# 구현과 완성

[공통 작업·문서 지침](../_shared/personal-workflow.md)을 읽고 필요한 부분을 적용합니다.

## 행동

요청에 여러 기능·변경이 포함되면 실제 코드에서 선행 관계와 수정 경계를 먼저 판단합니다. 독립적으로 구현·검증할 작업이 여럿이거나 여러 작업의 통합이 필요하면, 사용자가 명세·티켓·병렬을 명시하지 않아도 [병렬 구현·통합 지침](../_shared/parallel-delivery.md)을 읽고 작업 분할부터 통합 후 검토까지 이어갑니다. 같은 파일의 작은 수정처럼 나눌 이점이 없는 작업은 아래 흐름으로 직접 끝냅니다. 병렬화를 위해 제품 구조를 바꾸지 않습니다.

1. 요청한 동작과 완료 조건, 관련 코드·프로젝트 명령·기존 작업을 확인합니다. 기존 제품 완성 요청은 기존 요구와 실제 구현의 차이를 바탕으로 이어갈 단위를 선택합니다. 사용자에게 작업 목록이나 스킬 순서를 다시 작성하게 하지 않습니다. 분명한 작업은 별도 인터뷰나 계획 승인 없이 진행합니다. 결과를 바꾸는 업무 가정이 미확인이면 [질문 대상](../_shared/personal-workflow.md#정보-출처와-질문-대상)에 확인하거나 질문안을 건네고, 답을 기다리는 동안 그 가정에 의존하지 않는 부분부터 구현합니다.
2. 입력부터 사용자가 확인할 결과까지 필요한 연결을 구현합니다. 큰 변경은 동작 가능한 작은 단위로 진행하며 불필요한 계층·플러그인 구조·설정 옵션을 추가하지 않습니다.
3. 요구에서 기대 결과를 정하고 영향에 맞게 검증합니다. 사용자 관점의 동작과 실패 경계를 확인하며 구현 내부를 그대로 복제한 검증은 피합니다. TDD를 선택했거나 회귀 방지에 필요할 때 실패 사례를 먼저 확인합니다. 문구 수정에 새 테스트 체계를 만들지 않습니다. 업무 요구가 있는 작업은 동작한다는 사실과 확인된 업무 요구·예외 사례를 충족한다는 사실을 따로 대조합니다. 담당자에게 결과를 보여 재질문할 수 있으면 작은 동작 단위에서 차이를 확인하고, 불가능하면 확인된 요구와 사례로 대조합니다. 매 수정마다 형식적인 승인을 받지 않습니다.
4. 기능·구조·검증·남은 일이 달라졌으면 현재 문서의 해당 내용과 그림을 같이 고칩니다. 사소한 문구 변경이면 문서를 형식적으로 다시 쓰지 않습니다.
5. 실제 변경, 실행한 검사, 미검증 부분을 구별해 보고합니다. 완료한 단위를 상위 요청에 대조하고 남은 승인 작업이 있으면 이어갑니다. 사용자가 맡긴 범위를 충족하면 끝내며, 통과 후 선택 개선을 새 작업으로 시작하지 않습니다. 일부 외부 검증이 보류되면 그 결과에 의존하지 않는 남은 작업을 수행하고, 전체가 막혔다고 보고하지 않습니다.

작업 결과는 `완성한 동작 / 변경 위치 / 실제 검사 / 통합 상태 / 의존한 미확인 가정 / 남은 문제`를 필요한 만큼 보고합니다. 명세·작업 단위와 같은 용어를 사용하고, 작업자별 통과를 전체 연결의 성공으로 바꾸지 않습니다. 이해가 끊겼다는 신호가 오면 해당 판단에 의존하는 실행을 멈추고 배경부터 설명합니다.

## 예시

“메모 검색을 추가해줘”라면 입력·검색·표시를 연결하고 사용자가 관찰할 결과를 확인한 뒤 기존 문서의 흐름과 다음 작업을 갱신합니다. “빈 목록 안내를 바꿔줘”라면 해당 문구와 필요한 동작만 확인합니다. 검색 서비스·이벤트 시스템·일반화한 메시지 프레임워크를 만들지 않습니다.
