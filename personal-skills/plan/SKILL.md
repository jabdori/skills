# 접근과 작업 순서

[공통 작업·문서 지침](../_shared/personal-workflow.md)을 읽고 필요한 부분을 적용합니다.

## 행동

명세 작성이나 작업 분할 요청에는 [명세·작업 양식](../_shared/spec-and-tickets.md)을 읽습니다. 기존 문서의 관련 구역을 사용하며 별도 트래커를 만들지 않습니다.

1. 확정된 목적·완료 조건·제약과 실제 코드 구조를 확인합니다. 이미 정한 인터페이스와 선택은 새 근거 없이 다시 열지 않습니다. 구현을 바꾸는 요구는 [근거 상태](../_shared/personal-workflow.md#근거-상태-구분)를 구분하고, 미확인 가정에 의존하는 작업은 확인 뒤로 두거나 가정이 바뀌어도 다시 쓰지 않을 범위로 좁힙니다.
2. brief에서 정한 요구마다 저장·상태 관리 방식, 도구·라이브러리·런타임, 데이터 형식, 실패·재시작·동시성 동작, 외부 연동 중 결과·검증·설명에 영향을 주는 구현 결정만 전체 3~5개까지 찾고 사소한 선택은 묻지 않으며, 새 도구는 환경에서 사용 가능한지 먼저 확인합니다. 재시작 후 보존의 파일 저장·DB처럼 결과가 다른 대안이 있으면 `항목 / 선택: 미정 / 대안 2~3개와 각각의 한 줄 장단점(요구 충족·기존 환경/설치·검증·변경 부담) / 추천 이유 / 확인 방법`으로 먼저 보여 사용자 선택을 요청하고, 답 전에는 추천을 확정 구현으로 쓰지 않고 의존 작업을 조건부로 둡니다; 제약상 하나뿐이거나 자명한 선택만 이유 한 줄로 정하며, 사용자가 고른 결과는 요구 근거표에 `내 결정`으로 남겨 작업 단위에 연결합니다.
3. 사용자 동작 하나가 연결되는 구현 단위로 나누고 실제 의존성이 있는 순서만 정합니다. 새 추상화는 사용자가 알아야 할 복잡성을 실제로 줄일 때만 제안합니다.
4. 필요한 검증과 끝나는 지점을 정합니다. 계획·현재 구현·미확인 연결을 구분하고 구조도·시퀀스·분기 중 질문에 맞는 표현을 선택합니다.
5. 기존 현재 문서가 있다면 관련 계획과 다음 행동을 그곳에 남깁니다. 채팅 설계만 요청했으면 답변으로 끝내고 파일 생성·설치·서비스 실행을 하지 않습니다.

## 구체적인 산출물

- **명세:** 목표·요구 근거·현재와 변경 후·사용자 흐름·범위·공유 계약·완료 조건·검증·미정 선택을 합성합니다.
- **작업 단위:** 완성할 사용자 동작·선행 작업·수정 책임과 공유 지점·완료 조건·확인 방법을 정합니다. 요청된 명세를 이미 읽었다면 다시 인터뷰하지 않습니다.
- **순서:** 실제로 먼저 필요한 변경을 앞에 둡니다. 독립 작업은 병렬 후보로 표시하되 같은 파일·계약·검사 자원 충돌을 확인합니다. 코드의 폴더가 다르다는 사실만으로 독립이라고 판단하지 않습니다.

업무 용어는 기존 의미 지도와 맞춥니다. 명세의 계약과 작업별 완료 조건이 이어지고 다음 구현을 시작할 수 있으면 계획을 마칩니다.

## 종료와 예시

다음 구현 단위를 수행할 수 있는 정도면 끝냅니다. 모든 미래 기능을 분해하거나 새로운 승인 단계·작업 관리 체계를 만들지 않습니다.

“시각화 문서 하나로 정리하는 설계만 보여줘”라면 Markdown의 내용·그림·갱신 시점을 설계합니다. 서버나 문서 앱을 만들지 않고, 설계 요청을 코드 작성 허가로 해석하지 않습니다.
