# 접근과 작업 순서

[공통 작업·문서 지침](../_shared/personal-workflow.md)을 읽고 필요한 부분을 적용합니다.

## 행동

명세 작성에는 [한 파일 명세 양식](../_shared/templates/spec.md)을 씁니다. `brief`가 합의해 둔 앞부분은 다시 인터뷰하거나 덮어쓰지 않습니다.

참고: [Matt Pocock의 to-spec](https://github.com/mattpocock/skills/blob/main/docs/engineering/to-spec.md)·[to-tickets](https://github.com/mattpocock/skills/blob/main/docs/engineering/to-tickets.md)·[implement-spec](https://github.com/mattpocock/skills/blob/main/docs/engineering/implement-spec.md), [MIT 라이선스](https://github.com/mattpocock/skills/blob/main/LICENSE)를 시험용 한 파일 흐름에 맞춰 적용합니다.

1. 확정된 목적·완료 조건·제약과 실제 코드 구조를 확인합니다. 이미 정한 인터페이스와 선택은 새 근거 없이 다시 열지 않습니다. 구현을 바꾸는 요구는 [근거 상태](../_shared/personal-workflow.md#근거-상태-구분)를 구분하고, 미확인 가정에 의존하는 작업은 확인 뒤로 두거나 가정이 바뀌어도 다시 쓰지 않을 범위로 좁힙니다. 큰 과제는 시작에 `필수 규칙 충족 > 필수 산출물 > 품질 기준 > 부가 기능`의 우선순위와 남은 시간 배분을 정하고 독립 작업은 병렬 위임 후보로 표시합니다.
2. brief에서 정한 요구마다 결과를 바꾸는 결정만 고릅니다: 단계별 알고리즘, 기간 전체 고정/날짜별 선택, 판단 기준·가중치, 저장·상태·실패·재시작 방식, 계산과 화면·입출력의 경계, 주요 값 등이 해당합니다. 큰 과제에서 3~7개를 넘기지 않고 새 도구는 사용 가능 여부를 먼저 확인하며, 각 선택지 2~3개를 같은 작은 예시의 결과·정확성·규모·검사 쉬움·변경 부담으로 비교해 추천하고 사용자가 고른 말과 이유를 ADR에 남깁니다. 자명한 선택은 이유 한 줄로 끝냅니다.
   선택지 끝에는 `1A 2B처럼 답하고 이유 한 줄을 적어 주세요`라고 붙이고 답을 받은 뒤에만 구현 결정을 `docs/spec.md`와 ADR에 반영합니다.
   계산과 화면·저장의 경계는 [코드 구조 기준](../_shared/personal-workflow.md#코드-구조-기준)을 기본 추천으로 보여 주고, 합쳤을 때 생기는 문제와 사용자가 고른 이유를 해당 ADR에 남깁니다.
   정해지지 않은 주요 값은 담당자 답·확인한 일반 기준·제공 데이터에서 추정한 값을 구분해 ADR에 출처를 쓰고, 운영자가 바꿀 수 있는 설정을 기본으로 추천하며 실제 값을 바꿨을 때의 결과도 결정 조건에 넣습니다.
3. 작업 단위는 자료→계산→저장→화면·API→검사를 얇게 관통해 조각 하나만으로 사용자 동작을 확인할 수 있게 나눕니다. 지정 형식이 있으면 계약 검사기를 첫 조각에 넣고, 가장 단순한 입력부터 출력까지 통과하는 걷는 뼈대부터 얹습니다. 번호별 조각과 먼저 끝나야 할 막힘 관계를 사용자에게 한 번 보여 크기가 맞는지 확인한 뒤 `docs/spec.md`의 한 표에 남깁니다. 시험에서는 조각별 파일·하위 에이전트·통합 브랜치를 기본으로 만들지 않고, 막힘 없는 독립 조각에만 허용된 하위 에이전트를 고려합니다.
4. 필요한 검증과 끝나는 지점을 정합니다. 계획·현재 구현·미확인 연결을 구분하고 구조도·시퀀스·분기 중 질문에 맞는 표현을 선택합니다.
5. 계획 결과는 [문서 지도](../_shared/personal-workflow.md#문서-지도)의 `docs/spec.md` 뒷부분에 남기고, `docs/task/start-path.md`에는 명세 링크만 덧붙입니다. 결과를 바꾸는 결정은 [ADR 양식](../_shared/templates/adr.md)으로 `docs/adr/`에 하나씩 기록하고 명세에서 연결합니다. 큰 과제의 ADR은 3~7개만 남겨 결정마다 [로컬 커밋 규칙](../_shared/personal-workflow.md#로컬-커밋)에 따라 커밋하며, 뒤집으면 새 번호로 만들고 이전 것을 `대체됨: 새 번호`로 표시합니다.

요구에 최적화·배정·경로·일정·충돌이 있으면 문제 유형의 이름을 [쉬운 말 기준](../_shared/personal-workflow.md#쉬운-말-기준)으로 풀어 주고, 방법 2~3개를 제공 데이터의 같은 3줄에 적용해 `무엇을 / 왜 / 결과를 어떻게 확인하나`의 문장으로 표에서 비교합니다(자료가 없으면 가상 예시 표시). 규모·정확도·구현 시간·검사 쉬움을 비교해 규칙 검사기 → 단순 해 → 개선 순서를 추천하고, 사용자가 고른 이유와 다른 방법의 한계는 해당 ADR에 남깁니다.

선택지의 순서는 ① 입력 ② 작은 숫자로 계산 ③ 결과와 쓸 수 없는 조건으로 보여 주고, 먼저 넣거나 비교하는 이유와 ID가 가리키는 경우를 그 자리에서 설명합니다.

## 산출물

`docs/spec.md` 한 파일의 계획 구역과 ADR 링크가 실제 구현 순서·완료 조건·확인 방법을 설명하면 끝냅니다. 코드 폴더만 다르다는 이유로 독립 조각이라고 판단하지 않습니다.

## 종료와 예시

다음 구현 단위를 수행할 수 있는 정도면 끝냅니다. 모든 미래 기능을 분해하거나 새로운 승인 단계·작업 관리 체계를 만들지 않습니다.

“시각화 문서 하나로 정리하는 설계만 보여줘”라면 Markdown의 내용·그림·갱신 시점을 설계합니다. 서버나 문서 앱을 만들지 않고, 설계 요청을 코드 작성 허가로 해석하지 않습니다.
