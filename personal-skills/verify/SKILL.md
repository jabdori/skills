# 검토와 판정

[공통 작업·문서 지침](../_shared/personal-workflow.md)을 읽고 필요한 부분을 적용합니다.

## 행동

통합 결과나 병합 전 검토에는 [검토·PR 양식의 검토 구역](../_shared/review-and-pr.md)을 읽습니다. 최종 변경 전체와 관련 사용자 경로를 명세에 대조하며 요청 밖의 저장소 전체 감사로 확대하지 않습니다.

1. 검토할 주장·기준·자료 범위와 읽기 전용 여부를 확인합니다. 이미 확인된 범위를 새 의문 없이 다시 감사하지 않습니다.
2. 요구사항·원본 자료·사용자 경로와 `docs/spec.md`가 있으면 그 스토리별 성공 기준·작업 단위 완료 조건에서 기대 결과를 정합니다. 독립 계산이 필요하면 검토 대상의 집계 함수를 다시 호출하는 것으로 대신하지 않습니다.
3. 관련 코드와 실제 결과를 대조하고 변경 영향에 맞는 검사를 실행합니다. [공통 지침의 검사 근거](../_shared/personal-workflow.md#실제-변경과-검사-근거)대로 실제 수집·실패·생략·종료 상태를 확인하며, 작업자의 완료 메시지나 과거 통과 기록만으로 판정하지 않습니다. UI 외관, 접근성, 실제 상호작용과 외부 연동의 증거는 서로 대신하지 않습니다. 기술적으로 동작하는지와 확인된 업무 요구·예외를 충족하는지도 따로 판정하며, [미확인 가정](../_shared/personal-workflow.md#근거-상태-구분) 위에서 만든 동작은 `가정 의존`으로 표시하고 요구 충족으로 바꾸지 않습니다.
   [코드 구조 기준](../_shared/personal-workflow.md#코드-구조-기준)에 비춰 시작 파일이나 요청 핸들러 안에 배정·순서·집계 같은 계산 로직이 남아 있으면 파일:줄과 영향을 경고합니다.
4. 문제는 재현 조건·사용자 영향·근거 위치와 함께 설명하고, 이번 요청·합의로 설명되지 않는 형식·이름·주변 정리의 변경 줄도 지적합니다. 문제없다는 판단도 확인한 범위에 한정합니다. 수정 요청이 없으면 문제 발견을 임의 수정 권한으로 해석하지 않습니다.
5. 기록 수정이 허용된 경우에만 현재 문서의 상태·검증 근거를 바로잡습니다. 읽기 전용 검토에서는 응답으로만 전달합니다.

병렬 구현의 검토에서는 작업자마다 통과했더라도 공유 계약·용어 의미·입출력 연결·검사 생략 여부를 별도로 확인합니다. 검토 결과는 범위·근거 있는 문제·실행한 검사·준비 여부와 한계로 정리합니다. 구현 후 수정까지 맡은 경우에만 실제 발견 문제를 고치고 관련 검사를 다시 수행합니다. 준비됐다는 판정이 게시·병합 권한은 아닙니다.

화면 과제는 [agent-browser 화면 확인](../_shared/agent-browser.md)을 반드시 수행해 주요 흐름을 클릭하고 역할별 스크린샷·확인한 것·못 한 것을 남깁니다. 도구가 없으면 제공 설치 스크립트부터 실행하며 화면 확인용 Playwright·Puppeteer·Selenium은 새로 설치하지 않습니다(과제가 자동 E2E 테스트를 요구하면 테스트만 예외입니다).

업무 요구의 판정 결과는 기록 수정이 허용된 경우 `docs/requirements/evidence.md`의 [요구 근거표](../_shared/templates/requirements-evidence.md)에 [쉬운 말 기준](../_shared/personal-workflow.md#쉬운-말-기준)으로 씁니다. `충족/가정 의존/미충족`의 뜻도 상태 칸에 `만들고 검사함 / 확인하지 않은 조건에 기대어 동작함 / 요구대로 동작하지 않음`처럼 풀고, 읽기 전용이면 응답으로만 알립니다.

같은 판정으로 `docs/requirements/acceptance.md`의 [인수 점검표](../_shared/templates/acceptance.md)에 요구사항별 쉬운 상태·원문 위치·검사 근거를 갱신하고, 읽기 전용이면 파일 대신 응답에 차이를 적습니다.

`docs/adr/README.md`의 번호·상태와 각 ADR의 선택·이유·검사가 실제 코드에 맞는지도 대조하고, 대체된 결정이 현재 선택처럼 남아 있으면 지적합니다.

결과를 크게 바꿀 수 있는 설정값은 값을 바꿔 실제로 돌린 전후 숫자를 한 줄로 남기고, 변화가 크면 담당자에게 재확인할 질문을 제안합니다. 실행하지 못했으면 민감도는 미확인으로 씁니다.

제출 전에는 필요할 때 작업 폴더에서 `python3 <docs/task/start-path.md에 기록한 스킬 공용 자료 경로>/scripts/presubmit.py`로 변경·생성물·[ADR 목록](../_shared/personal-workflow.md#문서-지도)을 확인합니다. 시작 SHA가 최초 커밋과 다르면 `docs/task/start-path.md`의 값으로 `--base`를, 보호 파일은 `--protect`, 검사는 `--test`, 계약 검사는 `--contract "명령"`으로 지정합니다. 기본 결정 경로는 `docs/adr/`이고 README가 다른 제출 파일을 요구하면 `--decisions 경로`로 지정합니다. 스크립트는 파일을 고치지 않지만 검사 명령의 부작용은 그대로이며 작은 수정에는 추가하지 않습니다.

검토 결과에는 [로컬 커밋 규칙](../_shared/personal-workflow.md#로컬-커밋)에 맞춰 커밋되지 않은 관련 변경을 지적하되, 읽기 전용 검토라면 직접 커밋하지 않습니다.

## 종료와 예시

Python 표준 `unittest` 탐색을 사용하는 프로젝트에서 기계적인 결과 판정이 필요하면 프로젝트 루트에서 `python -B <이 스킬의 절대 경로>/scripts/verify_unittest.py -s tests`를 실행합니다. `-p`와 `-t`는 기존 탐색 패턴·최상위 경로가 필요할 때만 전달합니다. 검사 진행은 stderr, 마지막 JSON 요약은 stdout으로 출력합니다. 보조 스크립트 자체는 파일을 만들지 않지만 실행하는 기존 테스트의 부작용은 그대로이므로 프로젝트의 실행 경계를 따릅니다. 종료 코드 0은 실행 테스트 성공, 1은 실패·오류, 2는 0개 수집·전체 생략·성공한 검사 없음·불완전 실행 등 근거 부족입니다. 일부 생략·예상 실패는 요약에 별도로 표시하므로 전체 요구 검증으로 확대하지 않습니다. 다른 검사 도구에 맞추려고 프로젝트를 바꾸거나 기존 검사와 중복 실행하지 않습니다.

스킬·하네스 자체를 검토할 때는 실제 변경·도구 결과와 사용자 요구 충족을 봅니다. 특정 스킬 이름이나 고정 호출 순서를 성공 기준으로 삼지 않습니다. 짧은 대표 요청과 정상 대조 사례를 새 문맥에서 확인하고, 한 번의 통과를 모든 모델·프로젝트의 보장으로 보고하지 않습니다.

요청한 판단을 근거와 한계로 설명할 수 있으면 끝냅니다. 새 실패나 미해결 위험이 없으면 전체 검사·독립 검토를 다시 추가하지 않습니다.

“검색 완료라는데 정말 되는지 읽기 전용으로 봐줘”라면 문서 주장과 실제 검색 동작을 대조합니다. 실패가 있어도 코드·문서를 고치지 않고 실패 입력과 관찰 결과를 알립니다. 부분 테스트 통과를 제품 전체 검증으로 보고하지 않습니다.
