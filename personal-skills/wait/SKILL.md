# 잠깐, 다시 설명

이해가 끊긴 설명과 연결된 의사결정·구현을 멈춥니다. 요청한 목표와 현재 진행 위치는 유지합니다.

위임한 작업이나 실행 중인 명령이 있으면 [병렬 지침의 중단과 재개](../_shared/parallel-delivery.md#중단과-재개)를 적용합니다. 설명하는 동안 해당 작업자가 계속 수정하게 두지 않습니다. 전체 중단 요청은 모든 활성 작업에 전달하고, 중단 확인 전에는 완료됐다고 말하지 않습니다. 단일 작업이고 실행 중인 명령도 없으면 별도 제어 절차를 만들지 않습니다.

무엇이 막혔는지 말하지 않고 부르면 직전 응답에서 가장 이해하기 어려운 개념 1~2개(계산 방식, 숨은 기준, 처음 나온 용어)를 스스로 골라 풉니다. 진행 상황 보고로 설명을 대신하지 않습니다. 응답은 이 순서로 씁니다.

1. **막힌 지점** 한 줄: 무엇을 풀어 설명하는지
2. **왜 필요한가**: 이것이 없으면 무엇이 안 되는지
3. **작은 숫자 예시**: 실제 데이터나 가상의 두 안으로 계산 과정을 표로 보여 줌(예: 단위가 다른 두 값을 기준값으로 나눠 맞추면 각각 몇이 되고, 비중을 곱하면 어느 안이 나은지)
4. **그래서 내가 정할 것·할 일**: 선택지가 있으면 무엇을 고르는 것인지
5. **지금 상태**: 맨 끝에 두세 줄만(무엇이 코드에 들어갔고 무엇이 아직인지, 앞서 본 결과가 어떤 기준의 결과인지)

[쉬운 말 기준](../_shared/personal-workflow.md#쉬운-말-기준)의 생략 금지를 그대로 적용합니다. 지금 풀려는 문제와 빠진 배경을 초등학생도 이해할 말로 풀고, 실제 예시·일상 비유·터미널 ASCII 그림을 필요한 만큼 써서 선택의 차이를 보여 줍니다. 짧게 하되 전제는 생략하지 않고, 처음 나온 용어는 쉬운 말로 한 번 풀며 이해 전에는 기술 선택을 떠넘기지 않습니다.

파일 사이 관계가 막히면 [데이터 지도](../_shared/templates/data-map.md)의 한 건 따라가기를 다른 실제 레코드로 한 번 더 보여 주고, 어느 열의 값이 다음 파일의 어느 열과 같아 이어지는지 말로 풉니다.

제안 자체가 이 작업에 불필요했다면 이유를 설명하고 줄입니다. 이해를 돕는 설명을 새 강의·시험·문서 생성으로 확대하지 않습니다. 이해했다는 가정으로 방금 멈춘 작업을 자동 재개하지 않습니다. 사용자가 계속하라고 하거나 설명과 계속 진행을 함께 요청했다면 기존 승인 범위와 진행 위치에서 이어갑니다. 별도 승인 양식은 필요하지 않습니다.

예: “통합 브랜치가 왜 필요해?”에는 여러 사람이 만든 변경을 모아 함께 동작하는지 확인하는 작업본이라고 설명하고, 현재 작업에 병렬 구현이 실제로 필요한지도 연결합니다. 원래 요청이 문구 하나 변경이라면 그 절차가 필요하지 않다고 바로잡습니다.
