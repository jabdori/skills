# 설명과 인계

[공통 작업·문서 지침](../_shared/personal-workflow.md)을 읽고 필요한 부분을 적용합니다.

## 행동

PR 본문이나 사람 검토용 변경 설명을 요청받으면 [검토·PR 양식의 PR 구역](../_shared/review-and-pr.md)을 읽고 기존 프로젝트 양식을 우선합니다. 사용자가 이해가 끊겼다고 알리면 `wait`의 방식으로 진행 위치를 보존하고 빠진 배경부터 다시 설명합니다.

1. 독자가 이해하거나 이어가려는 질문을 기준으로 실제 파일과 현재 설명을 확인합니다. 문서가 있다는 이유만으로 내용을 사실로 가정하지 않습니다.
2. 전체 연결은 구조도, 호출 순서는 시퀀스, 조건은 분기, 작업 현황은 짧은 목록이나 정적 표로 표현합니다. 그림 하나에 모든 세부 사항을 넣지 않습니다.
3. 설명 요청은 요청한 매체에 답합니다. 현재 문서 갱신이 작업 범위에 있다면 허용된 문서의 관련 부분만 수정하고, 수정 금지인 과제 지시문(README 등)은 읽기 전용으로 둡니다. 설명 때문에 제품 코드나 실행 환경을 바꾸지 않습니다.
4. 인계 요청이면 같은 문서에 배경·중요 결정·실제 작업본·실행 위치와 명령·확인 범위·남은 일·다음 수정 위치 중 빠진 정보만 보완합니다. 이미 충분한 기능 설명·명령·그림을 인계 양식으로 다시 쓰지 않습니다. 기존 상세 설명은 링크하고 별도 인계 파일을 기본으로 만들지 않습니다. 현재 재개에 필요하지 않은 작업 과정과 오래된 검증 이력은 덜어냅니다.
5. 기존 검증 기록과 이번에 직접 실행한 확인을 구분합니다. 인계 문서 정리만 요청받았다면 기록과 관련 코드부터 대조하고, 검증 이후의 관련 변경·구체적인 불일치·실행 확인 요청이 있을 때 필요한 검사만 수행합니다. 기존 기록을 자신이 재실행한 결과로 쓰지 않으며, 인계 자체를 이유로 전체 검사·모든 예제를 반복하거나 다음 작업자에게 매번 반복하도록 적지 않습니다. 독립 재개가 요청되고 사용할 수 있다면 원래 대화 없이 문서와 파일로 이어갈 수 있는지 실제 작업으로 확인합니다. 실행하지 않았다면 문서 준비와 독립 재개 검증을 구분합니다.

프로젝트의 ‘검사는 X로 실행한다’는 명령 안내를 ‘인계 문서만 정리해도 항상 X를 실행한다’는 의무로 넓혀 해석하지 않습니다. 인계·문서 변경에도 검사를 실행하도록 명시한 규칙이 있으면 그 조건을 따릅니다.

결정 설명이나 사후 질의응답 대비 자료는 [쉬운 말 기준](../_shared/personal-workflow.md#쉬운-말-기준)으로 `무엇을 하기로 했나 → 왜 → 코드와 검사에서 어디를 보면 되나 → 아직 모르는 것은 무엇인가`를 각각 한 문장으로 잇습니다. [근거 상태](../_shared/personal-workflow.md#근거-상태-구분)를 유지하고 AI가 정한 선택을 사용자의 판단처럼 쓰지 않습니다. 제출 전에 실제 구현·검사와 설명을 대조하며, 본인 경험을 묻는 문서의 답은 대신 쓰지 않습니다.

“왜 이 결과인가, 최선인가”에는 [공통 답 형식](../_shared/personal-workflow.md#왜최선인가-질문에-답하는-형식)으로 같은 실제 데이터를 다른 방법·순서에 넣어 본 숫자를 제시합니다. 결과 한 줄에서 값을 만든 함수 → 읽은 데이터 → 결정한 줄(파일:줄) → 이유로 거꾸로 따라가고, 가능하면 `docs/task/data-map.md`와 같은 한 건을 [해결 흐름](../_shared/templates/code-map.md#해결-흐름)의 단계 번호에 맞춰 추적합니다. 비교를 실행하지 못했으면 최선이라고 말하지 않고 더 나은 안은 ADR 갱신 후보로 제시합니다.

결정 기록·계약 검사와 경계 테스트 결과를 [설명 카드의 답안 재료](../_shared/templates/code-map.md)에 `결론 → 근거(파일:줄·검사·누가 말했나) → 한계`로 모으고, 확인되지 않은 말이나 사용자의 직접 판단을 지어내지 않습니다.

구현 단위 뒤에는 [알고리즘 순서 카드와 문제 해결의 조건 처리표](../_shared/templates/code-map.md#해결-흐름)를 실제 사용자 동작으로 갱신합니다. 단계·조건·답안 재료마다 대조한 커밋 SHA를 적고 각 문장을 코드 파일:줄·검사로 확인하며, 근거가 없으면 `계획만 있음/구현 안 됨`으로 표시합니다.

제출 전에는 [문서 지도](../_shared/personal-workflow.md#문서-지도)의 `docs/submission/notes.md`에 확인된 재료만 모아 사용자가 루트 제출 문서를 직접 쓰게 합니다. [코드 지도](../_shared/templates/code-map.md)는 `docs/explain/code-map.md`에 두고 `docs/requirements/evidence.md`와 해당 [ADR](../_shared/templates/adr.md)을 실제 코드·검사에 대조합니다. README가 별도 결정 제출 파일을 요구하면 그 파일은 지정 위치에 두고 ADR로 링크하며, 작업 문서를 루트 제출 문서에 섞지 않습니다.

제출 전에는 [코드 지도](../_shared/templates/code-map.md#코드-전체-지도)에 [책임 폴더](../_shared/personal-workflow.md#코드-구조-기준)별 역할과 모든 제출 파일의 핵심 위치(파일:줄)·입출력 연결을 실제 코드와 맞춰 적습니다.

제출 전 사용자에게 `읽기 지도` 5곳을 파일:줄로 줍니다: 알고리즘 핵심, 주요 값, 실패 시 상태 보존, 계산과 화면·저장의 경계, 권한 검사. 해당하지 않는 항목은 확인한 근거 위치와 함께 `해당 없음`으로 밝힙니다.

제출 전 최종 커밋에 맞춰 카드·조건표·답안 재료를 마지막으로 대조해 `말해도 되는 것(코드·검사로 확인됨) / 말하면 안 되는 것(계획만·미확인)`으로 나눕니다. 그 결과와 ADR·세션 기록에서 확인된 내용만 [서술형 한 장](../_shared/templates/essay-sheet.md)으로 `docs/explain/essay-sheet.md`에 여섯 주제 두세 줄씩 압축하고 `docs/README.md`에 연결합니다.

서술형 준비에서는 보이는 한 문장에 섞인 `무엇을·어떻게·왜·바꾸면·한계`를 짚어 주되 별도 하위 질문 목록을 답안에 복제하지 않습니다. 겉으로 하나만 물어도 단계·하는 일·이유·한계를 살펴 한 단락에서 결론 → 근거 → 한계로 답하게 돕습니다.

ADR과 코드 지도에는 [명세의 구현 결정](../_shared/templates/spec.md#구현-결정)에서 고른 알고리즘·자료구조 등 주요 선택을 `선택 / 대안 / 이유 / 한계`로 코드·검사에 맞춰 짧게 담습니다. 결과를 바꾸는 주요 값은 [코드 지도의 주요 값과 근거](../_shared/templates/code-map.md#주요-값과-근거) 표에 값·파일:줄·출처·바꾸거나 그대로 둘 때의 영향·확인 결과로 적고 해당 ADR에도 같은 근거를 연결합니다.

구조를 설명할 때는 계산 핵심과 화면·저장·입출력을 어디에 두었는지, 그 경계를 택한 이유와 합쳤다면 생길 문제를 [설명 카드](../_shared/templates/code-map.md)에 한 줄로 연결합니다.

응시자 본인의 경험·판단을 묻는 문서는 [공통 규칙](../_shared/personal-workflow.md#본인-경험을-묻는-문서)에 따라 답을 대신 쓰지 않고 기록에서 확인한 재료만 제시합니다.

제출 문서나 설명 카드를 정리해 실제 코드·검사와 대조한 뒤 변경이 있으면 [로컬 커밋 규칙](../_shared/personal-workflow.md#로컬-커밋)에 따라 커밋합니다.

PR 자료는 최종 변경의 요약·필요한 그림, 변경 전후 근거, 영향 범위와 되돌리기, 중요한 검토 지점을 담습니다. 검증 판정과 글 작성은 구별하고 요청되지 않은 게시·병합은 하지 않습니다. 설명에는 프로젝트의 용어 지도를 활용하며 새 전문 용어가 필요한 경우 의미를 먼저 풉니다.

## 종료와 예시

독자의 질문에 답하거나 인계받을 사람이 이어갈 정보가 준비되면 끝냅니다. 사용자가 연습을 요청했을 때만 이해도 확인 과제를 제시합니다.

“다른 개발자가 이어서 할 수 있게 정리해줘”라면 `docs/spec.md`의 현재 작업 단위·다음 막힘 관계를 실제 코드와 맞춥니다. 파일 복제·자동 스냅샷·별도 서버는 만들지 않습니다. “왜 이 순서야?”에는 선택 이유를 짧게 설명합니다.
