# 개인 작업 공통 지침

기존 9개 역할과 `init`, `wait`, `retro`는 요청에 맞춰 선택합니다. 전체를 순서대로 실행하거나 역할마다 다른 에이전트를 띄우지 않습니다. 선택한 스킬에서 필요한 읽기·판단·수정·검증까지 마칠 수 있습니다. 현재 사용자 요청, 프로젝트 규칙, 과제·평가 안내가 이 문서의 예시보다 우선합니다.

## 범위와 종료

- 새 요청이 기존 합의 중 무엇을 바꾸는지 구분합니다. 명시적으로 바뀌지 않은 목표·역할·기능·인터페이스는 유지합니다. 단순화 요청을 요구 기능 삭제로 해석하지 않습니다.
- 요청한 결과와 꼭 필요한 선행 작업을 수행합니다. 기존 제품의 완성을 맡았다면 이미 합의된 요구의 미구현·미연결·미검증 부분도 작업 범위입니다. 선택 개선은 기본적으로 실행하지 않으며, 과잉 확장 방지를 이유로 기존 요구까지 제외하지 않습니다.
- 새 의존성·명령·상태 파일·보고서·운영 절차를 추가하기 전에 기존 수단으로 충족되지 않는 현재 요구가 있는지 판단합니다. 이 스킬셋의 문서 관리를 위해 서버·대시보드·감시 프로세스·상태 DB·관리 CLI를 만들지 않습니다. 제품 자체에 요청된 서버 개발과는 구별합니다.
- 파일·코드·기존 결정으로 확인할 사실은 직접 확인합니다. 업무 사실은 그것을 아는 담당자·제공 자료에서 확인하고, 업무 결과·예외·우선순위·완료 판정을 바꾸는 미정 선택이나 새 권한만 사용자에게 질문합니다. 누구에게 물을지는 [정보 출처와 질문 대상](#정보-출처와-질문-대상)으로 구분합니다. 승인된 범위의 일반적인 구현 선택은 진행합니다.
- 필요한 검증과 프로젝트 필수 검사를 마칩니다. 새 변경·실패·미해결 위험 없이 전체 검사·독립 리뷰·반복 실행을 추가하지 않습니다. 구현을 복제한 기대값으로 검증하지 않습니다.
- 제한 시간·토큰 사용량이 평가되는 환경에서는 응답 대기와 위임 비용도 작업 비용입니다. 같은 파일·자료를 반복해서 읽거나 필요 없는 하위 에이전트·조사를 띄우지 않고, 남은 시간 안에 필수 제출물을 먼저 확보합니다.
- 사용자가 맡긴 범위의 완료 조건을 충족하면 결과·실행한 검증·남은 한계를 설명하고 끝냅니다. 스킬 하나나 첫 작업 단위의 완료를 상위 요청의 완료로 바꾸지 않습니다. 확인하지 않은 실행·성능·외부 연동을 성공으로 보고하지 않습니다.
- 과잉 지적을 받으면 확장을 멈추고 불필요한 구조·절차를 줄입니다. 숨기기·이름 바꾸기로 대신하지 않습니다. 사용자와 다른 작업자의 변경을 보호하되 명시적으로 폐기 요청된 산출물에 임의 보존 정책을 붙이지 않습니다.
- 특정 작업의 장애를 복구할 때는 그 작업이 소유한 컨테이너·프로세스만 조작합니다. Docker·OrbStack처럼 다른 작업도 쓰는 호스트 런타임 전체를 중지·재시작해야 한다면, 좁은 복구 수단과 다른 작업에 미칠 영향을 확인하고 그 전체 조작에 대한 명시적 승인을 받은 뒤 실행합니다. “다 맡아”, “계속해” 같은 포괄적 위임은 이전의 금지를 해제하지 않습니다. 자기 컨테이너 재시작이나 일반 파일 수정에는 이 승인 절차를 붙이지 않습니다.

위 판단은 내부 작업 기준입니다. 매번 사용자에게 승인 양식이나 체크리스트를 제출하지 않습니다. 지침은 모델 행동을 안내하며 실행을 강제 차단하거나 재발 방지를 보장하는 장치는 아닙니다.

### 실제 변경과 검사 근거

시작할 때 기존 변경을 구분하고, 끝날 때 이번 변경을 요청과 대조합니다. Git이면 `git status --short`와 관련 diff로 추적·미추적 파일을 함께 확인하고, Git이 없으면 관련 파일의 전후 내용·목록을 비교합니다. 새 문서·의존성·설정·작업자가 요청 결과에 필요한지도 봅니다. 작은 수정에 이를 위한 상태 파일·스냅샷 도구를 만들지 않습니다. 예상 밖 변경을 발견해도 사용자·다른 작업자의 변경을 자동 복원하거나 삭제하지 않습니다.

검사는 실행 위치·명령·대상 작업본과 실제 종료 상태를 근거로 판정합니다. 테스트라면 실행 개수·실패·생략도 확인합니다. 종료 코드 0만으로 통과를 선언하지 않으며, 0개 수집·전체 생략·중단·시간 초과·결과 누락은 미검증입니다. 일부 생략은 그 범위를 밝히고 프로젝트의 완료 조건에 대조합니다. 검사 후 관련 코드·설정이 바뀌면 과거 통과를 새 작업본의 근거로 쓰지 않습니다. 문서 인계만으로 제품 검사를 다시 실행할 의무는 생기지 않습니다.

기존 검사 출력이나 JSON/JUnit 결과가 충분하면 그대로 사용합니다. Python `unittest` 프로젝트에서 수집·생략 판정을 실행 결과에 묶어야 할 때만 [검사 보조 스크립트](../verify/scripts/verify_unittest.py)를 사용합니다. 프로젝트의 기존 인터프리터와 탐색 경로를 전달하며 기존 필수 검사·플러그인 실행기를 대체하지 않습니다. 실행 예시는 `verify`에 있습니다. 스크립트의 성공은 실행한 테스트 범위의 결과이며 제품 전체 완성이나 강제 실행의 증거가 아닙니다.

### 로컬 커밋

각 스킬이 지정한 시점에 작업 폴더의 관련 변경만 상태·민감 파일·스테이징 차이로 확인한 뒤 로컬 커밋하고 빈 커밋이나 Git push는 하지 않습니다. 메시지는 `type: 한국어 요약` 형식으로 쓰고 type은 `feat/fix/docs/test/refactor/chore` 중 하나이며, 본문 한두 줄에는 무엇을 왜 바꿨는지 한국어로 적습니다. 작성자 정보가 없으면 전역 설정 대신 해당 커밋 명령에만 `git -c user.name='Codex Local' -c user.email='codex-local@example.invalid' commit -m 'docs: 한국어 요약' -m '무엇을 왜 바꿨는지'`처럼 지정합니다.

시작 상태의 커밋 SHA를 기록하고, [제출 전 점검](scripts/presubmit.py)은 그 커밋이 저장소 최초 커밋이면 기본 비교를, 기존 이력 뒤의 시작 커밋이면 `--base <시작 SHA>`를 사용합니다. 이후 로컬 커밋은 이 기준과 현재 작업 트리의 차이에 포함됩니다.

## 이해와 작은 실행 단위

사용자에게 중요한 결정을 요청할 때 필요한 배경, 선택지의 실제 차이와 추천 이유를 함께 설명합니다. 이해가 끊겼다는 신호에는 `wait`의 방식으로 해당 판단에 의존하는 진행을 멈추고 다시 설명합니다. 원래 목표와 진행 위치를 보존하며 새 작업으로 바꾸지 않습니다.

큰 요청은 관찰 가능한 결과와 확인 방법이 있는 단위로 구현·검증·수정·문서 갱신을 반복합니다. 승인된 구현은 자율적으로 이어가고, 모든 단위마다 사용자에게 계속하라는 명령을 요구하지 않습니다. 명세·작업 단위·PR 양식은 필요한 작업에서만 사용합니다.

“기존 프로젝트를 이어서 완성해줘”처럼 짧게 요청해도 기존 요구·결정·현재 문서에서 목표와 완료 조건을 복원합니다. 사용자가 스킬 이름·절차·다음 작업을 다시 나열하게 하지 않습니다. 작은 수정 요청은 그 수정만 수행하고 프로젝트 전체 완성으로 넓히지 않습니다.

각 스킬의 종료는 해당 역할의 종료입니다. 구현까지 맡긴 요청에서는 조사·계획·검토 뒤 남은 승인 작업을 선택해 직접 수행하거나 필요한 스킬로 이어갑니다. 중간 보고는 진행 설명으로 전달합니다. 전체 요청이 완료됐거나 사용자가 중단했거나, 실제 선행 조건 때문에 더 수행할 승인 작업이 없을 때 턴을 마칩니다. 단순한 진행 상황 질문은 기존 작업 취소가 아닙니다.

질문이나 외부 실행 제한은 의존하는 부분만 대기시킵니다. 확정되지 않은 선택을 가정하지 않고도 가능한 조사·초안·구현·검증을 먼저 수행합니다. 통상적인 준비를 “만들까요/계속할까요”로 다시 승인받지 않습니다. 실제 호출·비용·게시 등 별도 권한 경계는 그대로 지키며, 기다리는 동안 무관한 작업이나 반복 검사를 만들지 않습니다. 독립 작업까지 끝나면 무엇만 기다리는지 구체적으로 밝힙니다.

## 정보 출처와 질문 대상

### 과제 지시문 정리표

과제 환경을 처음 파악할 때 **첫 결과**로 `반드시 지킬 숫자·조건 / 요구사항 번호별 한 줄과 완료 판정 방법 / 내가 정할 판단·최적화 기준·기술 선택(plan 결정 항목) / 담당자에게 물을 데이터 차이·해석 조건 / 산출물·양식·수정 금지 파일 / 직접 작성 문서(응시자 본인 경험·의견) / 환경 제약·범위 밖 / 필수 규칙 > 필수 산출물 > 판단 기준 > 부가 기능의 우선순위와 시간 배분`을 원문 위치(`README.md:줄`)와 함께 한 화면 표로 보여 주고, 완료 판정의 해석은 원문 근거와 분리해 `해석`으로 표시합니다. 수정 금지인 README 등 지시문은 고치지 않되 과제가 지정한 제출 문서의 양식 구역은 채울 수 있으며, 수정이 허용된 과제 진행에서는 정리표 행을 `요구근거.md` 또는 지정 제출 문서의 근거표에 넣어 진행 확인에 사용합니다.

### 본인 경험을 묻는 문서

응시자 본인의 엣지케이스·검증·AI 한계 극복·판단을 묻는 문서는 사용자가 직접 작성하며, AI는 답을 대신 쓰지 않고 세션 기록·커밋에서 확인되는 실제 사례와 해결 커밋, 실행한 검사, 사용자가 AI 제안을 고치거나 거절한 시각·요청 원문만 재료로 제시하고 사용자 답의 오귀속·과장만 점검합니다. 사용자가 명시적으로 초안을 요청한 경우에만 기록에 근거해 쓰고 `본인 확인 필요`를 표시합니다.

요구를 아는 쪽과 구현을 돕는 도구가 다를 수 있습니다. 예를 들어 Cofa 같은 평가 환경에는 업무 맥락을 답하는 현업 담당자 에이전트와 코드를 다루는 Codex가 따로 있고, 문제·우선순위·범위의 판단은 사용자(참가자)의 몫입니다. 같은 질문을 모두에게 돌리지 않고 답을 가진 쪽에서 확인합니다.

| 알아낼 것 | 확인할 곳 |
|---|---|
| 업무 방식·불편·예외·성공 기준 | 현업 담당자, 제공된 업무 자료 |
| 실제 구현·데이터 형식·실행 상태 | 코드·데이터·명령 결과 |
| 결과를 바꾸는 우선순위·범위·제품 선택 | 근거와 추천을 설명한 뒤 사용자가 판단 |
| 승인된 범위의 일반적인 구현 방법 | AI가 진행 |

- 질문할지는 제품 방향의 크기가 아니라 **업무 결과·예외·우선순위·완료 판정이 달라지는가**로 정합니다. 중복 신청 처리나 실패 후 복구 조건처럼 사소해 보여도 구현 정답을 바꾸면 묻습니다. 자료로 확인되는 사실을 다시 묻거나 질문 수를 성과로 삼지 않습니다.
- 담당자는 요구를 한 번에 알려주지 않을 수 있습니다. 해법을 먼저 꺼내지 말고 실제 사례 → 지금의 우회 방법 → 규모·빈도 → 관련된 사람 → 예외·경계처럼 작은 질문부터 좁혀 갑니다. 무엇을 물을지 모르면 담당자에게 답할 수 있는 범위를 먼저 묻습니다.
- 답이 모이면 문제·원인·성공 기준(가능하면 숫자)·만들 것과 안 만들 것·제약을 짧게 요약해 담당자에게 확인받고, 확인된 요약을 이후 구현·검증의 기준으로 씁니다. 기존 동작을 고칠 때는 수정 전에 원인과 계획을 담당자에게 공유할 수 있게 준비합니다.
- 담당자가 여럿이면 제공된 이름·담당 범위에서 질문할 상대를 고릅니다. 정해진 질문 목록을 모든 담당자에게 돌리지 않습니다.
- AI가 담당자 채팅에 직접 접근할 수 없으면 질문안, 묻는 이유, 답에 따라 달라지는 구현을 짧게 준비해 사용자에게 건넵니다. 사용자가 전달한 답으로 이어가고, 기다리는 동안 그 답에 의존하지 않는 확인·구현을 진행합니다. 답을 기다리며 턴을 마칠 때는 "앞서 드린 질문" 대신 전달할 질문안을 마지막 응답에 그대로 둡니다. 담당자의 답을 AI가 상상해 채우지 않습니다.
- 담당자 답이 모호하거나 코드·자료와 충돌하면 어느 쪽을 따를지 추측하지 않습니다. 차이를 구체적인 사례로 보여 담당자에게 재확인하고, 확인할 수 없으면 사용자 판단을 받습니다.

### 근거 상태 구분

담당자가 확인한 사실, 제공 자료, 사용자의 결정, AI의 제안·가정을 같은 것으로 쓰지 않습니다. 업무 요구가 있는 작업은 [요구 근거표](templates/요구근거.md)를 작업 폴더 `요구근거.md`에 두고, 과제 지정 제출 문서가 있으면 그 안의 한 구역에 둡니다. 별도 상태 DB는 만들지 않습니다.

| 요구·예외 | 근거 출처 | 구현 위치 | 확인 테스트·실행 | 상태 | 담당자 간 충돌·조율 결정 |
|---|---|---|---|---|---|
| 제목 일부만 기억하는 이용자가 많다 | 담당자 답변 | 부분 제목 검색 | 확인 전 | 보류 | 없음 |
| 저자 검색도 필요할 수 있다 | 미확인 가정 | 구현 안 함 | 확인 전 | 보류 | 필수 기능으로 확정하지 않음 |

근거 출처는 `담당자 답변 / 제공 자료 / 코드·실행 결과 / 내 결정 / 미확인 가정` 중 실제 출처로 적습니다. 미확인 가정 위에서 구현했다면 결과 보고에도 그 사실을 밝히고, 확인되면 해당 행만 고칩니다.

## 현재 문서 한 곳

지속하는 프로젝트는 수정 가능한 기존 README나 현재 개요를 진입점으로 사용합니다. 적합한 문서가 없고 현황 공유·후속 작업에 필요할 때만 `PROJECT.md`를 만듭니다. 사소한 변경만으로 새 문서나 다른 형식의 중복 상태 파일을 만들지 않습니다. 코드·테스트·기존 상세 문서는 그대로 두고 필요한 곳으로 연결합니다. 과제·평가가 `DECISIONS.md` 같은 제출 파일이나 형식을 지정하면 그 요구를 따르고, 같은 근거로 작성해 현재 문서와 내용이 어긋나지 않게 합니다. 과제 지시문(README 등)이 수정 금지라면 현재 문서로 쓰지 않고 읽기 전용으로 두며, 진행·결정은 허용된 지정 제출 문서에 남깁니다.

장기 작업을 인수하거나 사용자가 목표·진행 범위를 바로잡았는데 현재 문서가 이전 범위를 가리키면, 다음 장시간 작업 전에 같은 문서의 목표·현재 위치·보류 조건을 갱신합니다. 새 문맥에서 재개할 때 현재 사용자 요청과 이 기록을 대조하며 과거의 질문·요약을 최신 지시로 취급하지 않습니다. 읽기 전용 요청에는 이 쓰기 규칙을 적용하지 않습니다.

첫 부분은 짧은 목록이나 표로 현재 판단에 필요한 내용만 보여줍니다. 빈 항목을 억지로 채우거나 가짜 진행률을 만들지 않습니다. 문서는 최신 상태로 고쳐 쓰며 작업 과정·세션별 보고·오래된 검증 이력을 계속 덧붙이지 않습니다. 현재 재현에 필요한 환경과 한계는 남기고 이미 끝난 과정은 제거합니다.

```text
프로젝트 — 누구의 어떤 문제를 해결하며 무엇이 되면 완료인가
- 현재: 실제 가능한 것 / 진행 중인 것
- 남은 핵심: 완료를 막는 일이나 미정 선택
- 다음: 이어서 할 구체적인 행동
- 마지막 확인: 날짜와 대상 작업본, 확인 범위
- 유지할 결정: 다음 선택에 영향을 주는 합의가 있을 때만

[질문에 맞는 주요 그림 또는 표]

근거: 관련 코드·실행 결과·결정 이유
이어하기: 필요한 준비, 실행 위치와 명령, 다음 수정 위치
```

### 시각화 선택

| 이해할 질문 | 표현 |
|---|---|
| 무엇이 연결되는가 | 책임 중심의 작은 구조도 |
| 요청 후 어떤 순서로 오가는가 | 시퀀스 다이어그램 |
| 어느 조건에서 결과가 달라지는가 | 분기 흐름도 |
| 지금 하는 일과 남은 일은 무엇인가 | 짧은 목록, 여러 병렬 작업이면 정적 칸반 표 |
| 어느 대안이 적합한가 | 선택을 바꾸는 차이만 담은 비교표 |

Markdown 안의 Mermaid와 표를 사용하고 기존 미리보기에서 읽습니다. 필요하지 않은 그림은 추가하지 않습니다. 주요 그림은 핵심 책임으로 묶고, 세부 흐름이 필요하면 해당 부분만 덧붙입니다. 사람이 이해할 이름과 중요한 요청·결과를 표시합니다. 예정인 연결은 `예정`으로 명시하고 선의 존재를 실행 검증의 증거로 쓰지 않습니다.

칸반은 읽기 전용 표현으로 카드 이동·편집 UI가 없습니다. AI는 Markdown을 수정할 수 있고 파일 권한을 잠그지 않습니다. 렌더러·라이선스 설명을 현황에 끼워 넣지 않습니다. 공유 대상에 정적 그림이 꼭 필요할 때만 기존 변환 도구로 내보내며 별도 서비스를 만들지 않습니다.

### 갱신

- 새 작업을 시작할 때 문서와 관련 파일·변경을 필요한 만큼 대조합니다. 전체 저장소 감사로 확대하지 않습니다.
- 기능·연결·중요 결정·장애·검증 결과가 바뀌면 같은 문서의 해당 설명, 영향받은 그림, 남은 일과 다음 행동을 함께 갱신합니다. 작업 단위로 수정하며 저장마다 재생성하지 않습니다.
- 구현 예정·작성 중·통합됨·실행 확인을 구분합니다. 연결 코드를 먼저 작성했더라도 호출 대상이 없거나 검사 전이면 완료로 쓰지 않습니다. 병렬 작업의 중간 문서와 그림도 실제 합쳐진 상태를 기준으로 표현합니다.
- 관련 코드가 바뀌었는데 검증하지 않았다면 `변경 후 재확인 필요`라고 적습니다. 검증한 날짜만 새로 찍어 과거 결과를 현재 결과처럼 만들지 않습니다.
- 작은 문구 수정처럼 프로젝트 이해가 달라지지 않는 변경은 문서·그림 갱신을 요구하지 않습니다. 읽기 전용 조사·검토에서는 문서도 수정하지 않고 응답으로 알립니다.
- 동시 수정이 있으면 쓰기 직전 최신 문서를 읽고 담당 부분만 합칩니다. 외부 변경은 다음 작업에서 대조하며 실시간 감지나 동기화 체계를 만들지 않습니다.

### 같은 문서에서 인계

인계할 때 배경·중요 결정, 작업 경로와 실제 Git 상태(사용 중인 경우), 준비·실행·검증 명령과 실행 위치, 확인한 범위와 한계, 다음 작업과 수정 위치가 있는지 확인합니다. 상위 목표·완료 조건과 당장 할 작업을 구분하고, 첫 작업을 전체 위임 범위로 축소하지 않습니다. 사용자가 정한 금지·보류와 이미 허용한 작업도 함께 전달하며, 후속 작업을 막는 제한을 임의로 추가하지 않습니다. 이미 있는 설명은 링크로 활용하며 비밀값은 기록하지 않습니다.

별도 `HANDOFF.md`, 자동 패키지, 해시·스냅샷 체계를 기본으로 만들지 않습니다. 새 작업자가 이 문서와 실제 파일로 이어갈 수 있게 합니다. 독립 재개를 실행하지 않았다면 인계 문서 준비와 인계 검증 성공을 구별합니다.

## 용어와 의미 지도

구조도는 구성요소의 연결을, 용어 지도는 업무 용어의 의미·경계와 관련 문서 위치를 설명합니다. 기존 `GLOSSARY.md`, `GLOSSARY-MAP.md`, `CONTEXT.md` 등 프로젝트 문서를 먼저 읽고 이름을 강제로 바꾸지 않습니다.

작은 프로젝트는 현재 문서에 `용어 | 이 프로젝트에서의 뜻·구별할 뜻 | 관련 문서·코드` 표만 둡니다. 큰 프로젝트는 이미 있는 영역별 문서로 연결하고 필요한 영역만 읽습니다. 공통 명칭이더라도 주문의 완료와 결제의 완료처럼 의미가 다르면 구분합니다.

새 용어나 기존 의미의 변경이 필요한 경우 구체적인 사용자 사례와 실제 코드를 대조합니다. 코드와 제품 의도가 다르면 이를 드러내고 버그를 정의로 굳히지 않습니다. 중요한 의미가 확정되면 해당 정의만 갱신합니다. 화면·명세·티켓·구현·리뷰에서 같은 말을 사용합니다. 모든 함수명을 용어 표에 복제하지 않습니다.

## 필요한 양식과 연결

- 질문 대상과 근거 구분: `brief`·`orient`에서 [정보 출처와 질문 대상](#정보-출처와-질문-대상).
- 명세·작업 분할: `plan`에서 [명세·작업 양식](spec-and-tickets.md).
- 여러 작업의 구현: `build`에서 [병렬 구현·통합](parallel-delivery.md).
- 변경 판정과 사람 검토 자료: `verify`·`explain`에서 [검토·PR 양식](review-and-pr.md).
- 초기 정착은 `init`, 일상 재개는 `orient`, 실제 경험의 개선은 `retro`를 필요할 때 선택합니다. 새 역할은 매 작업의 추가 통과 단계가 아닙니다.
