# 명세와 작업 단위

`plan`에서 명세를 만들거나 여러 작업으로 나눌 때 읽습니다. 작은 수정에 이 양식을 전부 채우지 않습니다. 기존 명세·이슈 양식이 있으면 활용하고, 없으면 현재 문서의 해당 구역에 작성합니다. 새 트래커·파일 묶음·상태 데이터베이스는 필요하지 않습니다.

## 구현 명세

대화와 실제 프로젝트에서 확정한 내용을 합성합니다. 이미 합의한 것을 다시 인터뷰하지 않습니다. 아직 결정되지 않은 중요한 조건은 미정으로 남기고 의존하는 구현만 기다립니다.

```markdown
## 이번 변경의 명세
- 문제·목표: 누가 어떤 동작을 할 수 있어야 하는가
- 요구 근거: 구현·완료 판정을 바꾸는 요구와 예외, 각각의 근거(담당자 답변·제공 자료·사용자 결정·미확인 가정)
- 현재와 변경 후: 유지할 동작과 달라질 동작
- 사용자 흐름: 입력부터 결과까지, 필요한 실패 사례 포함
- 범위·제외: 이번에 할 것과 하지 않을 것
- 계약: 공유 인터페이스, 데이터 의미·형식, 오류 처리의 중요한 합의
- 완료 조건: 실제 관찰할 수 있는 결과. 업무 요구가 있으면 확인된 업무 사례로 표현
- 검증: 기대 결과, 확인할 경계, 기존 실행 명령과 위치
- 구현 결정: 항목 / 선택(아직 못 골랐으면 미정) / 대안 / 이유 / 확인 방법
```

요구 근거는 [근거 상태 구분](personal-workflow.md#근거-상태-구분)의 짧은 표를 그대로 쓸 수 있으며, 구현을 바꾸지 않는 사실까지 나열하지 않습니다. 코드·그림·용어는 실제 프로젝트에 대응시킵니다. 임의로 방대한 사용자 이야기나 미래 기능을 추가하지 않습니다. 검증 경계는 기존 사용자 진입점과 검사를 우선하고, 새 테스트 구조를 도입할 이유가 없으면 만들지 않습니다.

## 작업 단위

각 작업은 가능한 한 입력부터 확인 가능한 결과까지 연결되는 작은 사용자 동작입니다. 독립적으로 확인하기 어려운 공통 변경은 선행 작업으로 분리합니다. 광범위한 기계적 이관은 억지로 사용자 기능으로 쪼개지 말고 실제로 호환 상태를 유지할 순서로 구성합니다.

```markdown
### 작업 이름
- 완성할 동작:
- 선행 작업: 없거나 실제로 먼저 필요한 작업
- 수정 책임·공유 지점: 담당 코드 경계와 함께 사용하는 계약·파일·테스트 자원
- 완료 조건: 충족할 요구, 미확인 가정에 의존하면 그 가정
- 확인 방법: 실행 위치·명령·관찰할 결과
- 현재: 필요할 때만 진행 상태와 근거
```

작은 작업은 같은 내용을 한 표의 행으로 표현해도 됩니다. 번호나 작업 이름은 문서 안에서 참조하는 용도이며 별도 ID 체계를 만들지 않습니다. 계획 단계의 수정 위치는 추정일 수 있으므로 구현 전 실제 파일을 대조합니다.

## 순서와 병렬 판단

- 선행 작업이 완료돼 실제 작업본에 반영됐고 공유 계약이 정해진 작업만 시작합니다.
- 기능 이름이 다르더라도 같은 파일·스키마·공용 데이터·포트를 바꾸면 순차 수행하거나 책임을 조정합니다. 병렬화를 위해 불필요한 제품 리팩터링을 하지 않습니다.
- 완료 조건·의존성·수정 책임을 설명할 수 있으면 계획을 끝냅니다. 일반적인 분할 선택을 매번 재승인받지 않습니다. 범위나 제품 의미를 바꾸는 선택만 사용자에게 배경과 추천을 함께 설명합니다.
- 외부 이슈 생성·수정은 해당 권한이 있을 때만 수행합니다. 로컬 명세 요청이 게시 권한을 뜻하지 않습니다.
