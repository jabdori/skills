# 여러 작업의 구현과 통합

`build`에서 여러 작업으로 나누어 구현·통합할 때 읽습니다. 작은 변경은 스킬 본문의 일반 구현 방식으로 끝냅니다. 별도 오케스트레이터·서버·작업 상태 저장소를 만들지 않습니다.

## 시작과 책임

명세, 작업별 선행 조건, 현재 작업본, 실제 공유 파일과 검사 자원을 대조합니다. 명세·작업 단위가 아직 없으면 확정된 요구와 코드에서 완료 조건·공유 계약·수정 책임·선행 관계를 먼저 정합니다. [명세·작업 양식](spec-and-tickets.md)의 필요한 항목만 기존 현재 문서에 짧게 정리하고, 통상적인 분할 선택을 사용자에게 다시 승인받지 않습니다. 사용자에게 보일 결과와 완료 조건을 유지합니다. 하위 작업의 테스트 통과를 제품 전체 완료로 간주하지 않습니다.

병렬 구현을 요청받았거나 이 실행 방식을 적용할 필요가 있는 복수의 독립 작업에서는, 제공된 하위 에이전트 도구로 해당 작업을 위임합니다. 불필요한 역할별 에이전트를 만들지 않습니다. 사용할 수 없으면 순차 수행하고 병렬 검증했다고 보고하지 않습니다.

각 작업자에게 명세·작업 구역·관련 지침의 위치, 수정 책임, 공유 계약, 실행할 검사와 필요한 권한 범위를 전달합니다. 이미 있는 자료를 긴 요약으로 복제하지 않습니다. 현재 문서와 공유 진입점의 최종 편집 책임자는 한 명으로 둡니다.

위임 결과의 작업자 ID와 실행 중인 명령 세션을 현재 대화에서 추적합니다. 작업자에게 중단 요청 시 자신이 시작한 명령·하위 작업까지 멈추고 미완료 상태를 보고하도록 전달합니다. 중첩 위임이 필요하면 통합 담당자가 그 관계를 알 수 있게 합니다. 이를 위한 별도 작업 등록부나 감시 프로세스는 만들지 않습니다.

작업 경계가 겹치면 순서를 조정합니다. 격리가 필요한 Git 프로젝트에서는 기존 워크트리 도구를 사용하고 기준 작업본을 확인합니다. 사용자 변경을 초기화하거나 기존 브랜치를 강제로 재설정하지 않습니다. 분리된 파일을 안전하게 수정할 수 있는 작은 예제는 같은 작업본에서 수행할 수 있습니다.

## 진행과 통합

1. 선행 조건이 충족된 작업만 수행합니다. 각 작업자는 사용자 동작을 구현하고 해당 검사까지 마친 뒤 수정 파일·실제 결과·한계를 보고합니다. 별도 보고 파일은 필요하지 않습니다.
2. 통합 담당자는 완료된 변경을 한 작업본에 반영하고 실제 계약·호출·오류 처리를 대조합니다. 커밋·브랜치 병합·푸시는 현재 권한 범위 안에서만 수행합니다.
3. 공유 경계가 바뀌면 후속 작업자에게 필요한 차이를 전달합니다. 선행 조건 충족은 실제 통합 상태로 판단하며, 외부 티켓이 닫혔다는 표시만으로 판정하지 않습니다.
4. 연결된 사용자 경로를 실행해 각 부분이 함께 동작하는지 확인합니다. 격리 환경에서 누락되거나 건너뛴 검사를 통과로 바꾸지 않습니다. 필요한 데이터·환경에 접근하지 못하면 미검증으로 남깁니다.
5. 명세의 작업들이 통합된 뒤 변경 전체와 관련 호출 경로를 한 번 검토합니다. 독립 검토가 요청됐거나 복수 작업의 경계 확인에 필요하면 새 검토자에게 명세·최종 변경·검증 근거를 주고 `verify` 방식으로 검토하게 합니다. 아직 만들지 않은 후속 기능을 실패로 오인하는 중간 전체 리뷰는 하지 않습니다.
6. 확인된 문제는 이번 변경 범위에서 수정하고 관련 검증을 수행합니다. 새 변경·실패·미해결 문제 없이 광범위한 리뷰를 반복하지 않습니다. 해결하지 못한 중요한 문제가 있으면 완료로 보고하지 않습니다.
7. 현재 문서의 상태·영향받은 그림·검증·다음 행동을 갱신합니다. 필요가 끝난 작업자는 제공된 종료 도구로 닫습니다. PR 자료가 필요하면 [검토·PR 양식](review-and-pr.md)을 사용합니다. 실제 게시·병합은 요청 범위에 있을 때만 수행합니다.

## 중단과 재개

사용자가 전체 중단을 요청하면 새 위임·구현·통합·검사를 시작하지 않고 모든 활성 작업자에게 즉시 중단을 전달합니다. 이해가 끊긴 특정 판단만 멈추는 요청이면 그 판단에 의존하는 작업자를 대상으로 합니다. Codex의 `send_input`에서는 `interrupt: true`로 전달하며 대기열에 넣는 것으로 대신하지 않습니다. 다른 환경에서는 실제 제공된 인터럽트·취소 기능을 사용합니다.

작업자는 자신이 시작한 실행 중 명령도 중지합니다. 명령 세션의 중단 기능을 우선하고, 남은 프로세스가 있으면 실행 위치·명령·PID 등으로 이번 작업이 만든 프로세스와 자식을 확인한 뒤 그 대상만 종료합니다. 이름이 같다는 이유로 모든 Python·Node 프로세스를 종료하지 않습니다. 에이전트 종료만으로 분리된 셸 프로세스까지 종료됐다고 가정하지 않습니다.

통합 담당자는 중단 응답과 실행 도구의 상태를 확인하고 필요가 끝난 작업자를 `close_agent` 등으로 닫습니다. 사용자가 대기하는 동안 중단을 먼저 알릴 수 있지만 확인 전에는 모두 멈췄다고 단정하지 않습니다. 중단 시점의 부분 변경은 자동 병합·완료 처리·롤백하지 않습니다. 미완료 검사와 재개 위치는 응답 또는 이미 있는 현재 문서에 필요한 만큼 남깁니다. 읽기 전용 요청이면 문서도 수정하지 않습니다.

재개 요청 후에는 실제 파일·남은 프로세스·완료된 작업을 대조하고 멈춘 부분부터 이어갑니다. 이전 실행과 새 실행이 겹치지 않게 하며, 중단된 검사는 재사용하지 않습니다. 완료한 독립 작업을 이유 없이 다시 만들지 않습니다.

## 끝나는 지점

요청한 사용자 흐름, 필요한 검사, 통합 후 확인, 발견 문제의 처리 결과가 맞으면 끝냅니다. 설명되지 않은 검사 생략·미해결 문제는 명시합니다. 사용자가 매 작업마다 다음 명령을 내려야 하는 절차를 만들지 않되, 이해가 끊겼다고 알리면 해당 판단에 의존하는 진행을 멈추고 설명합니다.
