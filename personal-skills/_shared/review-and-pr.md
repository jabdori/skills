# 변경 검토와 사람 검토 자료

`verify`의 통합·병합 전 검토, `explain`의 PR 본문 작성에서 필요한 구역만 읽습니다. 검토는 변경의 적합성을 판단하고, PR 본문은 사람이 그 판단을 할 근거를 보여줍니다. 둘을 혼동하지 않습니다.

## 검토 결과

요구·명세, 최종 변경과 관련 호출 경로, 실제 검사 근거를 대조합니다. 합쳐진 결과의 계약·데이터 의미·오류·사용자 흐름을 확인합니다. 요청 밖의 전면 감사나 취향에 따른 리팩터링을 제안 목록으로 채우지 않습니다.

```markdown
검토 범위: 기준 작업본·명세·실제로 확인한 경로
판단: 확인한 범위에서 준비됨 / 수정 필요 / 근거 부족
업무 요구 대조: 업무 요구가 있을 때만, 요구별 충족 / 가정 의존 / 미충족

| 문제·사용자 영향 | 근거·재현 조건 | 필요한 수정·확인 |
|---|---|---|

실행한 검사와 미실행 검사:
남은 한계:
```

문제가 없으면 빈 표를 생략합니다. 검토만 요청받으면 임의로 수정하지 않습니다. 구현·통합 후 수정까지 맡은 작업에서는 발견한 실제 문제를 고치고 해당 경로를 다시 확인합니다. 준비됐다는 판단은 자동 병합 권한이 아닙니다.

## PR 본문

기존 저장소 양식이 있으면 그 형식을 우선합니다. 아래 내용은 필요한 근거를 빠뜨리지 않기 위한 기준이며 사소한 변경에서는 짧은 문단으로 합칠 수 있습니다.

```markdown
## 변경 요약
사용자가 겪던 문제와 달라진 동작. 필요하면 작은 그림·호출 흐름·diff.

## 확인 근거
- 변경 전: 실제 관찰한 실패·화면·제한. 관찰하지 않았으면 명시.
- 변경 후: 실제 결과, 실행한 명령과 조건.
- 미검증: 남아 있는 경우에만.

## 영향과 되돌리기
영향받는 사용자·데이터·호출자. 호환성 변화와 되돌리기 어려운 변경 여부.

## 검토할 지점
사람의 확인이 필요한 중요한 선택이나 남은 쟁점이 있을 때만.
```

설명은 최종 변경을 기준으로 다시 쓰고 중간 작업 일지를 나열하지 않습니다. 화면 수정에는 가능한 실제 화면, 동작 수정에는 실제 실행 근거를 사용합니다. 병합 영향이 없는 부분을 가상의 위험으로 채우지 않습니다. 프로젝트 문서나 검사 결과를 링크하고 같은 내용을 여러 곳에 복제하지 않습니다.

PR 초안을 요청하면 초안까지 작성합니다. 생성·업데이트·게시·병합은 각각 현재 승인 범위를 따릅니다. GitHub PR을 실제 생성하거나 작업 대상으로 연결했다면 제공된 앱의 PR 첨부 도구를 사용합니다.
