# 구현과 완성

[공통 작업·문서 지침](../_shared/personal-workflow.md)을 읽고 필요한 부분을 적용합니다.

## 행동

요청에 여러 기능·변경이 포함되면 실제 코드에서 선행 관계와 수정 경계를 먼저 판단합니다. 독립적으로 구현·검증할 작업이 여럿이거나 여러 작업의 통합이 필요하면, 사용자가 명세·티켓·병렬을 명시하지 않아도 [병렬 구현·통합 지침](../_shared/parallel-delivery.md)을 읽고 작업 분할부터 통합 후 검토까지 이어갑니다. 같은 파일의 작은 수정처럼 나눌 이점이 없는 작업은 아래 흐름으로 직접 끝냅니다. 병렬화를 위해 제품 구조를 바꾸지 않습니다.

호스트·공유 자원까지 조작할 수 있는 전체 권한으로 여러 단계의 큰 작업을 장시간 자율 실행할 때만, 첫 변경 전에 `brief` 방식으로 사용자 결과, 소유·금지 자원, 끝까지 확인할 사용자 흐름과 검증 방법을 제공 자료·대화에서 짧게 고정합니다. 이미 정해진 내용은 다시 묻지 않고, 빠지거나 충돌하는 경계·완료 판정만 확인합니다. 별도 양식이나 매 단계 승인을 만들지 않으며 명확한 작은 수정은 바로 진행합니다.

1. 요청한 동작과 완료 조건, 관련 코드·프로젝트 명령·기존 작업을 확인합니다. 기존 제품 완성 요청은 기존 요구와 실제 구현의 차이를 바탕으로 이어갈 단위를 선택합니다. 사용자에게 작업 목록이나 스킬 순서를 다시 작성하게 하지 않습니다. 분명한 작업은 별도 인터뷰나 계획 승인 없이 진행합니다. 결과를 바꾸는 업무 가정이 미확인이면 [질문 대상](../_shared/personal-workflow.md#정보-출처와-질문-대상)에 확인하거나 질문안을 건네고, 답을 기다리는 동안 그 가정에 의존하지 않는 부분부터 구현합니다.
   세션이 새로 시작됐고 `docs/spec.md`가 있으면 그 문서·해당 ADR·`git log`를 읽어 마지막 완료 조각과 다음 막힘 없는 조각부터 이어갑니다.
2. 입력부터 사용자가 확인할 결과까지 필요한 연결을 작은 단위로 구현하며, 기존 코드에서는 요청·합의로 설명할 수 있는 줄만 바꾸고 내 취향과 달라도 기존 스타일을 따라 무관한 코드·주석·형식·이름과 고장 나지 않은 부분은 손대지 않습니다. 관련 없는 죽은 코드는 보고만 하고, 내 변경 때문에 안 쓰이게 된 import·변수·함수만 지웁니다. 담당자가 확인한 예외와 실제 입력 경계는 처리하되 일어날 수 없는 상황의 방어 코드·오류 처리나 요청 밖 계층·플러그인·설정 옵션은 넣지 않고, 끝에 더 짧고 단순하게 쓸 수 있는지 한 번 점검해 가능하면 줄입니다. 새로 쓰는 주석·docstring·사용자에게 보이는 오류·안내 메시지는 한국어로 쓰고(식별자·명령·파일 이름은 원문), 영어 주석이 생기면 그 단위에서 한국어로 고칩니다. 기존 코드의 주석 언어는 바꾸지 않습니다. 전체화면 응시 환경에서는 파일 선택·저장 대화상자를 여는 구현을 피하고 내보내기는 화면 표시·서버 파일·복사 방식처럼 가능한 흐름으로 연결합니다.
   새 코드는 [코드 구조 기준](../_shared/personal-workflow.md#코드-구조-기준)의 맞는 책임 폴더에 두고, 시작 파일·핸들러에 계산이나 저장 로직이 생기면 그 단위에서 해당 로직만 옮깁니다. 단위 보고에는 어느 책임 폴더에 넣었는지 한 줄로 적습니다.
   해당 코드를 쓸 때 설치된 스택 스킬을 확인해 Go에는 `use-modern-go`, React에는 `vercel-react-best-practices`·`vercel-composition-patterns`·`shadcn` 등 실제 설치된 지침만 참고합니다. 준비한 스킬로 다룰 수 없는 예상 밖 기술이 필요할 때만 `find-skills`를 쓰고, 설치되지 않은 스킬이 있다고 가정하지 않습니다.
3. 요구에서 기대 결과를 정하고 영향에 맞게 검증합니다. 사용자 관점의 동작과 실패 경계를 확인하며 구현 내부를 그대로 복제한 검증은 피합니다. 지정 형식이 있으면 첫 단위에서 필수·정의 밖 필드, 형식·단위와 README의 숫자 규칙을 확인하는 계약 검사기를 만들고 [로컬 커밋 규칙](../_shared/personal-workflow.md#로컬-커밋)에 따라 실행합니다. 단위별로 해당하는 시작 직전·직후·마감·날짜 전환·현재 시각의 상태와 0·상한·빈 교대/날짜·만료 당일을 경계 테스트로 확인합니다. TDD를 선택했거나 회귀 방지에 필요할 때 실패 사례를 먼저 확인하며 문구 수정에 새 테스트 체계를 만들지 않습니다. 업무 요구 충족은 동작 여부와 따로 대조하고 담당자 재질문이 가능하면 작은 단위로 보여 줍니다. 매 수정마다 형식적인 승인을 받지 않습니다.
   화면이나 사용자 흐름을 바꾼 단위는 [화면 확인 도구](../_shared/agent-browser.md)가 없으면 설치 스크립트부터 실행하고, 자기 서버를 `open → snapshot -i → 주요 흐름 click → screenshot`으로 확인합니다. 두 역할이면 각각 확인하며 확인한 것·못 한 것과 스크린샷 경로를 보고합니다. 직접 화면 확인이 끝나기 전에는 `docs/spec.md`의 그 단위를 완료로 표시하지 않고, 화면 확인용 Playwright·Puppeteer·Selenium을 새로 설치하지 않습니다(과제가 자동 E2E 테스트를 요구할 때만 테스트 도구 설치는 예외입니다).
4. `docs/spec.md`가 있는 과제는 작업 단위를 표의 순서와 막힘 관계대로 진행하고, 계획이 바뀌면 구현 전에 명세를 먼저 고칩니다. 검증한 단위는 같은 표에서 `완료`로, 진행 중이거나 미룬 단위는 실제 상태와 이유로 갱신하고 영향을 받은 그림도 맞춥니다. 사소한 문구 수정에는 새 명세를 만들지 않습니다.
   180분 응시에서는 시작 뒤 110분에 새 구현을 멈추고 미완성은 한계로 적어 이해 구간으로 넘깁니다. 이후 꼭 필요한 수정도 20분을 넘기면 중단하고 확인한 범위만 남깁니다.
5. 단위 보고는 [쉬운 말 기준](../_shared/personal-workflow.md#쉬운-말-기준)으로 `사용자에게 보이는 결과 → 그 결과를 만든 코드 경로` 순서로 말하고 실제 검사·미확인을 구별합니다. ID는 어떤 경우인지 밝히며 `성공·실패·여유`에는 숫자로 판정 기준을 붙입니다. 구현 중에는 학습 질문으로 멈추지 않고 승인된 다음 단위를 이어갑니다.

업무 요구가 있는데 이 `SKILL.md`가 있는 폴더 기준의 [요구 근거표](../_shared/templates/requirements-evidence.md)가 없으면 `docs/requirements/evidence.md`에 만들고, `HOW_TO_RUN.md` 같은 제출 문서에는 섞지 않습니다. 자료를 못 찾으면 `| 요구·예외 | 근거 출처 | 구현 위치 | 확인 테스트·실행 | 상태 | 담당자 간 충돌·조율 결정 |`로 시작하며, 구현·검사를 마친 단위마다 위치·검사·상태를 갱신합니다.

계획에 추천이 있고 사용자가 선택 없이 구현을 맡기면 추천을 적용하되 `docs/requirements/evidence.md`와 해당 ADR에 `AI 추천 채택(내 이유 없음)`으로 남기고 이유 한 줄을 요청합니다. 사용자가 `추천대로`라고만 해도 사용자 고유의 이유를 지어내지 않습니다.

결과를 바꾸는 주요 값(상수·임계값·기준일·필터·기본값·제외 데이터)을 새로 넣거나 유지·변경하면 값과 근거 출처를 근거표·해당 ADR에 남기고, AI의 임의 선택 외에 근거가 없으면 사용자에게 알려 정하게 합니다.

README·자료에 없는 계산 값은 코드에 박지 않고 설정으로 두며 가능하면 운영자가 바꾸게 합니다. 담당자 답·확인한 일반 기준·데이터 추정 중 어느 근거인지 ADR에 적고, 선택하지 않은 값을 확정처럼 쓰지 않습니다.

검증을 통과한 구현 단위마다 관련 코드·검사·문서를 [로컬 커밋 규칙](../_shared/personal-workflow.md#로컬-커밋)에 따라 커밋합니다.

새 파일을 만든 단위가 끝나면 역할·핵심 함수·입출력을 짧게 보고합니다. 모든 단위의 읽을 곳(파일:줄)·나중에 답할 질문·커밋 SHA는 `docs/explain/code-map.md`의 `이해 구간에서 볼 곳`에 쌓고 보고에는 그 한 줄만 보여 줍니다. 그 자리에서 답을 요구하지 않습니다.

계획에 없던 새 저장소·라이브러리처럼 결과·검증·설명을 바꾸는 결정이 필요하면 [ADR 양식](../_shared/templates/adr.md)으로 같은 작은 예시의 대안·장단점·추천을 보여 선택을 받고, 새 번호의 ADR과 `docs/adr/README.md`를 갱신해 [로컬 커밋 규칙](../_shared/personal-workflow.md#로컬-커밋)에 따라 커밋합니다. 기존 결정을 뒤집으면 새 ADR을 만들고 이전 것을 `대체됨: 새 번호`로 바꾸며, 자명한 선택은 이유 한 줄로 끝냅니다.

작업 결과는 `완성한 동작 / 변경 위치 / 실제 검사 / 통합 상태 / 의존한 미확인 가정 / 남은 문제`를 필요한 만큼 보고합니다. 명세·작업 단위와 같은 용어를 사용하고, 작업자별 통과를 전체 연결의 성공으로 바꾸지 않습니다. 이해가 끊겼다는 신호가 오면 해당 판단에 의존하는 실행을 멈추고 배경부터 설명합니다.

## 예시

“메모 검색을 추가해줘”라면 입력·검색·표시를 연결하고 사용자가 관찰할 결과를 확인한 뒤 기존 문서의 흐름과 다음 작업을 갱신합니다. “빈 목록 안내를 바꿔줘”라면 해당 문구와 필요한 동작만 확인합니다. 검색 서비스·이벤트 시스템·일반화한 메시지 프레임워크를 만들지 않습니다.
