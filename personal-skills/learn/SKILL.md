# 내 작업 이해하기

목표는 제출 전 이해 구간에 실제 결과 한 건을 코드로 거꾸로 따라가고, 카드를 가린 채 스스로 설명한 뒤 빠진 것만 다시 보는 것입니다. 이 `SKILL.md`가 있는 폴더 기준의 [explain의 결정 설명](../explain/SKILL.md#설명과-인계)과 [설명 카드](../_shared/templates/code-map.md)의 근거 연결을 재사용하되, 자료를 못 찾으면 `| 빠진 개념 | 코드 위치(파일:줄) | 확인 근거 | 다시 답할 질문 |` 머리줄로 기록하고 학습 문서나 정답을 먼저 보여 주지 않습니다. AI 사용이 금지된 서술형이 시작되기 전 작업 시간에만 연습합니다.

1. 실제 코드·검사·ADR·대화와 접근 가능한 세션 기록에서 결과 한 건을 골라 제출 코드 전체의 동작을 추적합니다. 연습 문항 6~8개는 업무·문제 해결의 말로 쓴 **한국어 한 문장**만 하나씩 보여 줍니다. 질문에는 파일·함수·클래스·변수 이름, 줄 위치, 코드 조각, 시각, 수식, 번호나 하위 목록을 노출하지 않고 실제 도메인 단어 대신 `[대상]`만 씁니다. 겉으로 하나만 묻되 단계 순서·단계마다 하는 일·그 순서의 이유·한계가 답에 필요한 모양(“[대상]을 선택한 알고리즘의 순서를 설명하세요”)과 요구 2~4개를 한 문장에 섞은 모양(“여러 조건이 겹친 문제를 해결하면서 무엇을, 어떻게, 어떤 순서로 처리했고, 그 이유는 무엇인가”)을 섞습니다. 문항마다 내부 평가 관점 2~4개를 정하며 조건 충돌·동점·규칙 위반, 주요 값 변경, 구조 경계, AI에 맡긴 일과 사용자가 확인한 일, 지침과 코드의 일치 중 실제 근거가 있는 것을 고릅니다. 담당자 답은 기록으로 확인될 때만 묻습니다. 내부 평가 관점·모범 답안·근거는 답변 전 힌트로 공개하지 않습니다.
2. 실제 결과 한 줄을 만든 함수·데이터·결정 근거로 거꾸로 따라간 뒤 [알고리즘 순서 카드·문제 해결의 조건 처리표](../_shared/templates/code-map.md#해결-흐름)와 [서술형 한 장](../_shared/templates/essay-sheet.md)을 가리고 한 문항씩 냅니다. 사용자가 보지 않고 답한 뒤에만 코드·실행 결과와 대조해 맞은 점과 빠진 점을 `평가 관점 1`처럼 번호를 붙여 짚고 모범 답안·근거(파일:줄)는 이 피드백에서만 공개합니다. 숨은 요구는 **겉으로 묻지 않았지만 좋은 답에 필요했던 것**이라고 구분해 알려 줍니다. 실제 제출물·결정 기록·실행 결과가 뒷받침하는 범위만 평가하고, 기록된 실행과 이번 실행, 확인하지 못한 사실을 구분합니다. 사용자가 직접 검증했다는 기록이나 선택 이유가 없으면 미확인으로 남기며, 사용자가 답한 범위를 넘어 의도·이유·성과를 지어내지 않습니다.
3. 틀리거나 빠진 단계만 [코드 지도](../_shared/templates/code-map.md)의 `학습` 구역에 짧게 남기고 서술형 직전에는 [서술형 한 장](../_shared/templates/essay-sheet.md)만 다시 보게 합니다. 답할 시간이 없으면 질문만 남기고 내부 평가 관점·모범 답안·근거는 답변 후 피드백까지 공개하지 않습니다.

`docs/explain/code-map.md`의 학습 구역을 정리해 변경이 생기면 [로컬 커밋 규칙](../_shared/personal-workflow.md#로컬-커밋)에 따라 커밋합니다.

시험·과제에서는 [ADR](../_shared/templates/adr.md)의 실제 결정과 코드를 읽고, 별도 학습 파일 없이 `docs/explain/code-map.md`에 틀린 개념만 남깁니다. 확인한 범위보다 크게 가르치지 않습니다.

본인 경험·판단을 묻는 필수 문서에는 [공통 규칙](../_shared/personal-workflow.md#본인-경험을-묻는-문서)에 따라 기록에서 확인한 재료와 답변 점검만 제공하고 사용자의 답을 대신 쓰지 않습니다.
